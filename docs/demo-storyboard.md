# Relayのデモ構成案

これは次の撮影・開発の提案。撮影済み映像や、新しいタスク成功の検証結果を示す文書ではない。
現在の構成は[Runtime](runtime.md)、既存映像と検証済み範囲は[提出ガイド](pai-submission.md)を参照。

## 第一候補：失敗の直前へ戻り、人間が「ここだけ」を修正する

伝えたいことは「AIが困ったところだけ直し、元の試行を残したまま、採用経路をデータとして取り出せる」。
新しいbackendの追加より、この流れを一つのタスクで最後まで見せることを優先する。

### 2分程度の構成

| 目安 | 見せる内容 | 視聴者に伝えること |
|---|---|---|
| 0:00–0:15 | 物体と目標、全体／手首カメラ、VLAによる操作 | 何を達成したいか |
| 0:15–0:30 | 実際に困った場面で停止。問題の位置を字幕で示す | 全部をやり直す必要があるのか |
| 0:30–0:45 | 分岐図の直前stepをクリックして復元 | ロボットと物体が前の状態に戻る |
| 0:45–1:05 | H、Space＋WASD/RF等で必要な箇所だけ修正 | 人間が直した部分がはっきり動く |
| 1:05–1:25 | PでVLAへ返す。達成できた場合は結果を映す | 人間とAIが一つの操作をつなぐ |
| 1:25–1:45 | 元の経路と修正経路を分岐図で示し、修正側を採用 | 元の失敗を消さずに経路を選べる |
| 1:45–2:00 | 出力先と、採用step数・操作の出所を示す | 見た目のデモからデータ収集につながる |

最初はLIBEROで、接続するVLA checkpointが対象としているタスクから選ぶ。
短い事前試行で、実際にモデルが進められる部分と介入が必要な部分を見つける。
都合のよい失敗や成功がまだ得られなければ、その状態を結果として記録する。
GenesisのLIBERO用checkpoint接続確認だけを根拠に、Genesisで把持タスクを解けるとは扱わない。

手動区間は、カメラ上で移動が分かる数秒を確保する。現在の速度調整と手首カメラを使う。
VLAの推論待ちを編集で省く場合は字幕で示し、実時間で滑らかに動いたようには見せない。
本番は実モデルを接続した状態で撮影し、TEST providerの確認映像とは区別する。
成功条件は環境の判定と映像の両方で確認し、コード終了やstep増加を成功と取り違えない。

### データとして見せる範囲

- `route.jsonl`：採用した操作経路。
- `vla-candidates.jsonl`：観測・指示・実行action・出所の対応。
- `vlm-code-candidates.jsonl`：条件を満たす完了コードがあれば収録。
- `program-coverage.jsonl`：中断／一部採用等によってコード候補から外れた理由。
- `selection.json`：経路の選択とhash。学習投入は別工程で`training_admitted=false`。

手動やVLAだけの映像では、コード候補が0件でも正しい。
手動操作から意味的なPythonコードが自動生成されたとは説明しない。

## 追加候補1：LLMがVLAへ任せ、人間が途中で引き継ぐ

自然言語からLLMが短いPythonコードを生成し、その中の`run_vla()`で局所操作をVLAへ委譲。
人間が途中でHを押して調整し、必要なら新しいLLM指示で続きを始める。
コードの一部と制御の出所を映すと、三者がどう協力したかを説明しやすい。

必要なtool・外部LLM接続・VLA接続・中断の仕組みは既存。
実LLMと実VLAの両方を使う一連のタスクの成功は、別途通しで確認する必要がある。
中断したPythonプログラムをその行から自動再開する機能はない。
新しい指示からの再生成と、コード内のboundedなVLA呼び出し後の復帰を区別する。

## 追加候補2：同じ状態から修正案を二つ試す

一つのcheckpointから、手動修正Aと、LLMコードによる修正Bを別々の分岐に残す。
どちらの経路を採用するか、元の映像と分岐図を見ながら選ぶ。
同じ環境・scene内の復元を使い、branchごとの操作量や結果を記録する。
少数の映像比較からモデル全体の優劣や成功率を主張しない。

分岐・復元・採用は既存。A/Bの同期再生や映像の並列比較UIは未実装なので、
まずは別々に録画した素材を明記して編集する。ROS 2参照版は巻き戻し非対応。

## 今回の残作業と、その後の開発

1. Runtime分離のPR #10を確認してmainへ統合する。
2. 第一候補の短い通し試行を行い、対象タスク・介入地点・実際の結果を固定する。
3. 一続きの実演を撮影し、記録の出所・採用経路と照合してから動画と説明資料を更新する。

追加実装を一つ選ぶなら、保存した二つの分岐の観測画像を同期して比較する閲覧UIが候補。
その次に、採用経路のプレビュー・品質確認・データ形式別exportを検討する。
標準的な学習形式への変換には、action単位・camera・時間間隔等の対応を定義して検証する必要がある。
現時点で標準形式への学習投入まで完了したとは扱わない。

YouTubeへのアップロードや提出済み資料の差し替えは、この構成案を書いた時点では実施していない。
